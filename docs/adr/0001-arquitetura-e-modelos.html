ADR 0001 — FinGuard: Arquitetura multi-agente e seleção de modelos

Documento: FinGuard / Future Minds 3 (Zup) · Versão: 1.0 · Data: 2026-07-27

1. Contexto 2. Opções de arquitetura consideradas 3. Decisão final 4. Consequências e trade-offs 5. Análise de custos estimada 6. Recomendações de segurança 7. Atualização pós-implementação

1. Contexto do problema

Instituições financeiras recebem milhares de reclamações por dia, em texto livre, por múltiplos canais (SAC, Ouvidoria, Redes Sociais, Banco Central, Procon). A triagem manual é lenta, inconsistente entre analistas, e o maior risco não é a demora — é o erro de escalonamento: uma reclamação com indício de fraude ou menção a órgão regulador que não é tratada como crítica gera multa, dano de imagem ou violação de LGPD. O dataset fornecido para o desafio (~500 reclamações fictícias) também contém tentativas reais de prompt injection (extração de system prompt, jailbreak via persona, inversão de regras), simulando um vetor de ataque real contra o próprio sistema de IA.

2. Opções de arquitetura consideradas

Opção A — Classificador único (chamada única de LLM)

Um único prompt recebe o texto e devolve todos os campos (categoria, produto, sentimento, urgência, resumo, risco) em uma chamada. Mais simples de implementar.

Rejeitada: mistura responsabilidades (classificação e análise de risco/conformidade no mesmo prompt), dificulta auditoria (não há separação entre "o que é" e "o que fazer a respeito"), e não atende ao requisito de nível 2/3 de arquitetura multi-agente com responsabilidades distintas e rastreáveis.

Opção B — Multi-agente genérico, sem guardrail nem RAG (nível 2 puro)

Grafo com agente de triagem, agente de risco e agente de relatório, mas sem proteção de entrada/saída e sem consulta à política interna — decisões de urgência dependem só do bom senso do prompt.

Rejeitada: não resiste às tentativas de prompt injection presentes no próprio dataset, não é auditável (parecer de risco sem base documental) e não atende aos requisitos obrigatórios de nível 3 (guardrails, RAG, ADR).

Opção C — Escudo de Compliance: multi-agente + guardrails de entrada/saída + RAG na política interna (escolhida)

Mesma espinha dorsal de agentes da Opção B, acrescida de: nó de guardrail obrigatório antes de qualquer processamento, RAG sobre a política interna (POL-SAC-001) para fundamentar o parecer de risco com citação de cláusula, e guardrail de saída para blindar dado sensível.

3. Decisão final

Adotar a Opção C. O grafo segue a estrutura:

_start_ → guardrail_entrada → [BLOCK] resposta_bloqueio → __end__
guardrail_entrada → [PASS] agente_triagem → agente_risco → agente_relatorio → guardrail_saida → __end__

Cliente de LLM abstraído atrás de uma interface única (LLMClient), com duas implementações intercambiáveis por variável de ambiente: OpenAIClient para desenvolvimento local (sem acesso a Bedrock na máquina pessoal) e BedrockClient (boto3) para execução real, usando o Guardrail já provisionado (ID + version 1) na conta AWS do projeto Vivo (cliente Zup do usuário) — acesso corporativo de projeto, já testado e validado, uso restrito à janela do desafio. Ver COMPLIANCE.md §2 para o registro do risco residual dessa escolha frente à regra de "ambientes de execução" do desafio. Essa divisão de client existe unicamente para viabilizar o desenvolvimento em duas máquinas diferentes — a saída avaliada e a demo final rodam sempre em BedrockClient.

4. Consequências e trade-offs

  • Positivo: cada agente é testável e auditável isoladamente; erro de um agente não contamina silenciosamente os outros; guardrail como primeiro nó garante que nenhuma reclamação é processada sem checagem, mesmo em caso de falha de outro componente.
  • Positivo: RAG citando cláusula específica torna o parecer de risco defensável perante compliance/regulador — não é uma "caixa preta" dizendo apenas "Crítica".
  • Trade-off: mais chamadas de LLM que a Opção A (uma por agente, não uma só) — mitigado usando modelo barato (Nova Micro) nos agentes de menor complexidade e reservando modelo mais caro (Claude Haiku) só para o agente de risco.
  • Trade-off: desenvolver com OpenAIClient e avaliar com BedrockClient introduz risco de divergência de comportamento entre modelos de famílias diferentes — mitigado com bateria de teste completa na máquina Zup antes do evento (ver PRD, seção 8).

6. Recomendações de segurança

  • Guardrail de entrada é sempre o primeiro nó do grafo — nenhum caminho de código pode chamar os demais agentes sem passar por ele antes.
  • Guardrail de saída combinado com verificação determinística por regex (CPF, número de conta) como camada extra — não depender só do julgamento do modelo para dado sensível.
  • Resposta de bloqueio nunca deve ecoar ou explicar a instrução maliciosa recebida, nem revelar detalhe de configuração interna (mensagem fixa, genérica, em português).
  • Logs de execução não devem persistir o texto original da reclamação além do necessário para a demo — evitar reter dado (mesmo fictício) além do escopo do desafio, seguindo o espírito da política de dados do POL-SAC-001 (seção 5).
  • Todo recurso de nuvem que gera custo (guardrail, se criado especificamente para o desafio) deve ser desprovisionado imediatamente após o evento, conforme regra de compromisso do desafio.

7. Atualização pós-implementação (validação real, tarefa 3.4/3.5)

Esta seção registra o que a validação real na conta AWS do projeto Vivo/Zup mudou em relação ao que este ADR previa — decisão consciente de manter o histórico em vez de reescrever silenciosamente, para a banca poder ver o raciocínio real, não só o resultado final.

  • Guardrail Bedrock precisou de ajuste manual. Um guardrail criado sem configuração explícita de Prompt Attacks não bloqueou nenhum dos ~10 casos de prompt injection do dataset (action: NONE em todos). Habilitar o filtro Prompt Attacks (força High) resolveu o caso clássico de jailbreak por persona, mas não os pedidos de extração disfarçados de legítimos (auditoria, documentação, pentest). Foi necessário adicionar um Denied Topic customizado ("extração de configuração interna") com exemplos tirados diretamente do dataset. Aprendizado: guardrail do Bedrock não vem pronto pra esse tipo de ataque só por existir — precisa configuração deliberada, testada contra casos reais.
  • Resultado real: maioria dos ataques bloqueada, 2 casos ainda não confirmados (REC-2026-00413 e mais um) — aceito como risco conhecido e documentado (ver docs/TASKS.md, tarefa 3.1), não escondido. Mitigação estrutural: os agentes não têm nenhuma ferramenta de acesso a dado de outro cliente — mesmo um miss de guardrail não resulta em vazamento real de dado, porque o sistema nunca teve essa capacidade.
  • PassthroughGuardrail adicionado para desenvolvimento na máquina pessoal (sem acesso a Bedrock) — nunca bloqueia, avisa alto em todo uso, existe só pra permitir testar o resto do pipeline localmente sem depender de Bedrock. Só o BedrockGuardrail real conta para fins de avaliação.
  • 3 bugs reais encontrados durante a validação no Bedrock, todos corrigidos:
    1. 1 reclamação com resposta malformada (não-JSON) derrubava o processamento do lote inteiro — faltava tratamento de erro por item no orquestrador do grafo.
    2. Nenhum dos dois clients de LLM tinha limite de max_tokens configurado — corrigido (600 tokens, com folga sobre o observado em produção real de 80-130 tokens de saída).
    3. agente_risco citava a seção de produto (procedimento, ex: 3.3) em vez da seção de urgência/canal (o motivo do risco, ex: 2.x/4.x) em pelo menos 1 caso real — corrigido com regra de preferência explícita no prompt e reforçada com regra dura no código.
